## Existing System Comparison Mandate

Compare current live logic, V2/V3/old systems, shadow systems, and newly generated systems on same-denominator evidence wherever the data permits exact comparison. When exact same-denominator comparison is not possible, build the strongest honest comparable evidence, quantify the gap, and create the repair/forward-capture path that would make exact comparison possible. If one system appears materially better than current live on comparable evidence, preserve that as a first-class challenger. Do not protect the incumbent. Do not assume old live logic is sacred.

For each challenger, capture:

- denominator;
- sample size;
- effective independent denominator;
- symbol/session/regime coverage;
- horizon/target family;
- controls;
- costs/friction assumptions;
- failure modes;
- exact code path or mechanical rule;
- what would need to change in production code;
- what to shadow;
- what to kill.

## Failure Intelligence Doctrine

For every failed or weakened idea, classify it as one or more of:

- false opportunity/generic movement;

- underpowered branch;

- mixed mechanism needing split;
- inverse/avoid-filter candidate;

Then do the next useful thing: repair, split, control-adjust, preserve residual, build avoid logic, route forward capture, or kill the exact unsupported claim.

## Continuous Improvement Loop

Until the 60-hour wall-clock expires, repeat:

1. Inventory what is known.
2. Ask what is missing.
3. Search/build/extract the missing evidence.
4. Generate all possible mechanical hypotheses from the evidence.
5. Test them against controls.
6. Diagnose success and failure.
7. Repair/split/adjust/preserve/kill exact claims.
8. Build stronger code or stronger data.
9. Compare against current and prior systems.
10. Update ledgers.
11. Spawn subagents for every independent track where parallel depth, breadth, adversarial review, source search, implementation, or verification can materially improve the sprint.
12. Move to the next deepest open path.
13. Reopen the frontier map and add new fields/markets/algorithms/sciences to study.
14. Reopen the question avalanche ledger and convert unanswered questions into work.
15. Challenge the best current system by building unrelated challengers.

If the loop appears exhausted, broaden the universe: more markets, more horizons, more source roots, more target families, more strategy families, more controls, more old research, more production-code improvement ideas, more execution realism, more risk policies, more external research.

Never attach to one idea, fail it, and stop. If one idea dies, use its failure to open more routes. If one market is empty, search other markets. If one system underperforms, build challengers. If one strategy family collapses under controls, study why and move to another family. The sprint must actively search, generate, test, repair, and improve across independent paths for the full 60 hours.

## Output Standard At 60 Hours

At the end of the window, produce:

- an executive synthesis of what was discovered;
- all material strategies/hypotheses/systems tested;
- all surviving mechanisms;
- all killed mechanisms and why;
- all systems that beat current live on comparable evidence;
- all production code proposals;
- all validation gaps;
- all data gaps;
- all next highest-value routes;
- exact instructions to reproduce results;
- exact commits made;
- exact files changed;
- exact checks/tests/recomputes run;
- exact unresolved access requests;
- confidence levels by claim.
- a survival verdict for this moonshot lane: continue/expand/integrate, continue only with exact changes, or terminate/archive as insufficient.

The final answer must not pretend certainty where evidence is weak, and it must not weaken opportunity to appear cautious. State uncertainty exactly, convert uncertainty into next evidence paths, keep opportunity intelligence alive, and be bold in discovery, hard in testing, exact in evidence, and relentless in improvement.

## Prompt-Hardening Addendum

This addendum preserves the objective above and makes the control language explicit for mechanical launch validation.

Evidence-class posture: branch-local research, discovery, source acquisition, data engineering, replay, controls, proposed implementation, and no-promotion synthesis. The sprint must pursue proof-or-impossibility to the full end inside every same-evidence-class route it opens. A blocker is not terminal until it is cleared, proven impossible from approved routes, or reduced to an exact owner/access/source/capture requirement. Same-evidence-class pursuit is mandatory; split only when the next action crosses into a new evidence class such as independent G12/G0 acceptance, promotion, live behavior, paid spend requiring approval, credentials/remotes, or a forbidden broker/account/order/history/deal/position surface.

Forbidden surfaces: no live prompt/config/risk/execution/safety/canary/selector/order-behavior changes may be treated as deployed production changes; no paid API/vendor/Databento spend may run without the required pre-call manifest and external approval mechanism; no broker account/order/history/deal/position evidence may be used in a lane that forbids that evidence class; no promotion, validation, R/PnL, win-rate, expectancy, live-readiness, or live-effect claim may be made without a separate promotion dossier.

Safe flags for all sprint artifacts unless a later separately approved lane changes them:

- `NO_PROMOTION_VERDICT`
- `validation_safe=false`
- `outcome_review_opened=false`
- `live_effect=false`

Completion audit requirement: before any terminal closeout, build a prompt-to-artifact completion audit that maps every explicit requirement, named context file, command, gate, artifact, test, verifier, ledger, data route, subagent route, and deliverable in this prompt to concrete file or command evidence. Passing tests, manifests, or substantial effort are not sufficient by themselves; the audit must show real coverage of the prompt requirements and list every missing, weakly verified, or intentionally deferred requirement with the exact proof-or-impossibility reason.
