# Goal Session Research Discipline

Date: 2026-05-10
Status: active instruction
Scope: GTOS `/goal` research sessions, outcome-testing lanes, source/as-of lanes, and packet-builder lanes

## Owner Intent

The owner wants research sessions pushed to their practical maximum. Do not treat a `/goal` as a quick summary task. Treat it as a proof-seeking research run that must actively close ambiguities, chase missing context, and leave durable artifacts.

This does not mean uncontrolled outcome-peeking, spending, live-trading changes, or weak production-change assertions. The intended mode is:

Aggressive research, strict production-change evidence.

Builder/audit posture split: evidence-building, discovery, repair, packet, replay, and candidate-edge prompts should be output-maximizing and aggressively constructive inside their evidence class. They should build every source-safe artifact, neutral target, derivation contract, expansion contract, failure anatomy, and auditable result the lane allows. G12/G0 audit prompts should be adversarial and acceptance-focused. Do not import G12 skepticism into builder prompts in a way that makes them timid, self-censor valid outputs, or stop at "no edge found" without exhausting the allowed search.

Prompt framing controls search behavior. Future prompt prep must assume that a goal session will tend to find what it is primed to find: if it is framed mainly as a falsification exercise, it will find reasons to break an idea; if it is framed as a creative source-safe discovery/build task, it will look wider. Therefore builder, discovery, evidence-capture, replay, repair, and candidate-edge prompts must explicitly prime breadth, curiosity, outside-the-current-box mechanisms, and non-obvious route search. They must not be dominated by defensive "fake result" language. The correct builder instruction is to build the strongest auditable, source-bound artifact possible, label evidence classes precisely, and leave independent rejection or acceptance to G12/G0.

Gate-language hygiene rule: weak gated language creates weak sessions. In builder, discovery, result-packet, result-screening, source-expansion, and constructive G0 synthesis prompts, do not frame the objective as "do not interpret", "route only", "control evidence only", or "future work" unless the prompt also states exactly what must be computed, searched, extracted, joined, ranked, and explained now. Boundaries should be written as hard forbidden surfaces and evidence-class labels, not as psychological brakes. A result-screening prompt must explicitly say that quarantined numerical intelligence is required when accepted rows already exist; it must not hide behind the fact that live-scale or production-change assertions remain gated.

Maximum-intelligence rule: the purpose of research lanes is to find ideas, strategies, hypotheses, filters, mechanisms, inversions, and failure explanations that can become stronger after source control, sealed validation, stress testing, and forward realism. Evidence-class boundaries must never be used as reasons to stop interpreting source-bound data, to avoid difficult questions, to skip ugly negative/inverse findings, or to fall back to the default "only existing OB edge" answer. Constructive G0/result-screening prompts must require a data-generated question stack: every ambiguity, contradiction, positive slice, negative/inverse slice, neutral slice, failure cluster, non-applicable group, duplicate/concentration effect, horizon/target-family asymmetry, partition reversal, descriptor contrast, and outlier found while answering one question must be added to the stack and pursued inside the same evidence class until answered, killed with data-backed reason, proven impossible, or handed to an exact separate evidence-class route.

Active-prompt embedding rule: it is not enough for these principles to live in this context file. The actual controlling prompt being run must carry the anti-boxing and constructive-search instructions directly in its objective, route-ranking, saturation, completion, and one-line starter sections. If the active prompt still centers warnings, negative closure, defensive limitation language, or a narrow list of examples, the preparing agent has not done its job. Builder/discovery/G0 route-selection prompts must say that examples are not limits, current GTOS edges/frameworks are not the horizon, and the session should find as many useful source-safe route families as the evidence class allows before ranking them. G12 can filter later; the constructive prompt should not pre-suppress discovery by priming fear of rejection.

Terminology guardrail: even "source-safe" can become conservative if it is used as a vague brake. In constructive builder/discovery/G0 route-selection prompts, define it as auditability and no-leak/hard-boundary discipline, not as narrowness. Prefer phrasing like "auditable, hard-boundary-compliant route families" when the goal is breadth. The active prompt should make clear that this requirement does not limit creativity, data modalities, route count, hypothesis families, instruments, sessions, timeframes, or mechanism search. G12 can later reject weak evidence; the builder/control prompt must not self-censor useful discovery paths merely because they are novel or not already accepted.

The program must not collapse back into the default answer "no new edge, only the existing OB retest edge" unless the lane has actually searched the broader source-safe hypothesis space and produced machine-checkable negative evidence. Current GTOS edges and known frameworks are starting baselines, not the research boundary. Future prompts must actively ask what adjacent or orthogonal mechanism could exist beyond the current production logic, what data can expose it, and what source-safe artifact would let G12 judge it.

Three research virtues are mandatory for this program:

- Curiosity: actively look for ways the system could improve, search beyond the obvious files and common trading-strategy framing, and keep asking what else could explain or unlock the mechanism.
- Truthfulness: never fake, soften, rescue, or cover a failure. If an idea fails, say exactly how and why it failed from the data. If evidence is missing, say what is missing. If the result is negative, keep it negative and learn from it.
- Active creativity: do not be boxed by norms, known strategies, the current GTOS edge, familiar indicators, default timeframes, or the first scientific framing. Generate new angles and views, then let source-safe data and preregistered tests decide. Creative hypotheses are welcome; post-hoc validation claims are not.

The source of truth is the market data and source-bound evidence, not reputation, convention, or what a strategy is commonly believed to do. A goal session should be imaginative in proposing search routes and mechanisms, but strict and honest in evidence handling.

## What "Go All The Way" Means

For research/control lanes, every session should:

- complete mandatory GTOS preflight before using memory or old summaries;
- reconstruct the evidence chain from original prereg or hypothesis through packet, source contract, result lane, red-team audit, and current G0/G12 synthesis;
- search local artifacts first, including builders, JSON/JSONL, source projections, manifests, scripts, tests, raw/cached folders, shadow logs, relevant `git log` and `git show` history, and neighboring lane outputs;
- actively hunt contradictions, stale context, duplicate denominator errors, label-family confusion, hidden leakage, source/as-of gaps, legal/access ambiguity, parser/cache/hash gaps, and missing approval gates;
- when a field or source is missing, keep searching until local pursuit is exhausted, then write negative evidence that states exactly what was searched and the exact missing file, field, source, parser, logger, schema, legal proof, owner approval, or budget proof needed;
- request access when needed instead of silently giving up;
- use official/public webfetch or curl only when the lane authorizes source-contract evidence and local cache is insufficient, then save raw captures and a source index;
- run all non-outcome verification that fits the lane, such as JSON parse, schema checks, source-hash recomputation, no-leak scans, duplicate/denominator audits, label-family checks, `py_compile`, and focused pytest;
- produce files and commits, not chat-only conclusions.

Anti-boxing rule: prompt examples, artifact lists, and known data roots are starting points, not boundaries. A goal session must actively check whether it is accidentally boxed by timeframe, worktree-local files, data modality, instrument, science domain, model class, latest-summary artifacts, access path, or the first framing of the question. If a relevant route exists in local heavy data, another research lane, source contracts, code history, papers, cached docs, read-only extraction paths, or approved web/source tooling, the session should pursue it or write the exact approval/source/as-of/no-leak reason it cannot. The only hard boundaries are forbidden live trading surfaces, outcome leakage, uncontrolled spend/API use, source/as-of invalidity, credential/remote changes, and production-change assertions.

Persistence rule: do not stop because the work is long, multi-step, or inconvenient. A `/goal` research session should keep pursuing relevant allowed questions until it reaches a frozen artifact, exact proof of impossibility, an exact owner/access/source/capture approval requirement, or a hard forbidden boundary. The completion audit should show the pursuit path and not hide behind generic "future work" wording when the next step could have been done inside the current goal.

Speed is not a research-quality constraint. A goal session must not choose a weaker artifact, compact-only sample, shallow route, or "good enough" answer merely because the complete pursuit takes longer. If the allowed evidence class supports a full run, full aggregation, exhaustive search, or deeper same-class pursuit, the session should run it, checkpoint it, stream it, chunk it, or resume it. Runtime becomes a blocker only when there is an exact resource failure, forbidden boundary, unavailable approval/access, or proven impossibility from approved routes; the completion audit must record that proof.

Completion-as-exhaustion rule: in result-screening, source-expansion, discovery, and failure-anatomy lanes, marking complete is an assertion that no known useful same-evidence-class intelligence remains unextracted from the accepted artifacts. The lane must maintain an exhaustion or coverage ledger listing the files, fields, partitions, screens, comparisons, interactions, candidate examples, failure views, and recursive follow-ups inspected; if any same-class screen remains feasible, the lane continues. "We found enough" is not a completion standard.

No arbitrary top-N rule: a goal session must not cap questions, blockers, limitations, opportunities, datasets, open doors, closed doors, route families, candidate examples, partitions, or findings at an obvious number like top 3, top 5, or top 10 unless the underlying full ledger is also preserved. Rankings are useful summaries, not evidence replacement. If a lane finds many relevant items, it should write all of them to machine-readable artifacts and then provide ranked slices for readability.

Same-evidence-class continuation rule: blocker classification is not a sufficient stop condition when the next route is still inside the same evidence class and inside the prompt's safety boundaries. If a source/as-of lane discovers multiple blocker natures, it should pursue every source-safe blocker family inside the same goal until each is cleared, proven impossible from approved routes, or reduced to an exact owner/access/source/capture requirement. If a packet-builder lane discovers missing input fields, it should pursue allowed packet/source reconstruction rather than only naming the missing family. If a forensics lane discovers a failure mechanism, it should pursue available row-level failure anatomy rather than stopping at "negative result." The session may split only when the next step crosses an evidence-class gate, becomes materially too large/risky, or requires approval/access that cannot be obtained inside the run.

Repair-before-handoff rule: a blocker ledger is not completion. A next-route prompt is not completion. A clean fail-closed classification is not completion when same-evidence-class repair is possible. If a goal discovers a missing field, stale hash, source gap, geometry gap, denominator ambiguity, control ambiguity, path/fillability ambiguity, cost/slippage gap, target/stop gap, side/entry/stop/target/fillability/R-geometry gap, or incomplete result condition that prevents the strongest computation, it must pursue repair inside the same goal using every already-approved local/source-bound artifact and every available historical, MT5, Sierra, shadow/log, research, route-local, and accepted upstream source allowed by the prompt. After repair, it must recompute the affected artifacts, manifests, hashes, verifiers, focused tests, and ledgers. Leave a blocker unresolved only with exact owner/access/source/capture impossibility or proof that repair requires a different evidence class that the route cannot open. Even then, the output must contain exact row-level repair requirements and the next route must be concrete execution/repair, not an abstract G0/G12 loop.

Decision-progress anti-ladder rule: pursuing every ambiguity, open door, question, limitation, and opportunity does not mean creating a separate goal session for each one. A strong goal session should keep the ambiguity stack inside the same run, pursue it aggressively, repair what it can, compute what it can, and then make the concrete research or implementation decision it was asked to make. Repeated sequences of G0 -> G12 -> repair -> G0 -> G12 for the same evidence class are fake productivity when they defer the same decision without crossing a true evidence-class boundary. When the owner asks for a decision, the goal must not use "emit the next prompt", "needs another audit", "needs another synthesis", "needs capture", "missing geometry", or "proof of impossibility" as its final product. It must choose among the explicit decision alternatives in the controlling prompt, state the evidence, and record the implementation or research-priority action. Safe flags remain mandatory rails, but they are not permission to stay in research forever without concrete decisions.

Result/scoring/validation repair rule: these routes must not stop at neutral movement if trade-geometry repair may be possible. They must attempt to bind side, entry/reference, stop/invalidation, target/R multiple, horizon, fillability/path ordering, and cost/slippage from accepted SCID candidates, source-control packets, repaired target rows, M1/M15 path ledgers, forward-capture schemas, live/shadow logs, Sierra/MT5 historical sources, moonshot-compatible historical sources, route-local artifacts, and accepted upstream sources. If exact R/expectancy remains impossible, compute the strongest available proxy and preserve row-level missing-field proof. "Not broker/live actual performance" is an evidence-class label, not a reason to avoid sealed historical/proxy/source-bound R-style metrics where geometry can be source-bound.

Recoverable-source rule: a missing source blocker is not automatically final. The session must distinguish recoverable historical market data from non-generatable historical system-state truth. Missing ticks/bars/quotes/spreads may be recoverable through approved read-only local roots, broker exports, MT5 read-only copy routes, Sierra/vendor caches, or explicitly approved source pulls, with hashes and as-of/source-contract proof. Missing pending-lifecycle intent, order-observability, write-clock, ticket-redaction, or logger fields can be reconstructed only if source-safe logs/artifacts already recorded enough information; otherwise they are true historical source gaps and must be closed prospectively by capture/logger contracts. Never generate, infer, or backfill historical intent/order/lifecycle truth from price movement alone. If a lane hits this class, it must either recover the exact source evidence, prove it cannot exist from approved routes, or create/verify the forward capture requirement that prevents recurrence.

No-local-data blocker rule: "not in this worktree" or "not local" is never a final answer. A goal session must escalate through absolute local roots, prior worktrees, broker/Sierra/vendor caches, read-only extraction paths, and approved access manifests before it records a missing-data blocker. The final blocker must name the exact missing symbol/window/field/source, every searched root or extraction route, and the exact next action required from the owner or a future capture/logger lane. If the data is obtainable, the session should obtain or request it; if the data is non-generatable historical source truth, the session should prove that and freeze the prospective capture fix.

Standing owner-access pursuit rule: the owner has given standing intent for goal sessions to go all the way inside the prompt's allowed evidence class. A session must not stop at "needs approval", "needs access", "owner export required", or "blocked by missing local data" when the blocker can be solved by an allowed source-safe action that the agent can run, request via the approval tool, or route through existing local/broker/Sierra/vendor/read-only extraction tooling. If a command or filesystem/network/source access requires runtime approval, ask for the exact permission and continue after approval. A final owner/access request is valid only when the needed action cannot be executed in the current session, is outside the route's evidence class, requires unavailable external credentials/manual export, requires paid/API spend not authorized by the prompt, touches forbidden broker account/order/history/deal/position/live behavior, or has been proven impossible from approved routes. "Ask and stop" is incomplete when "ask, receive approval, and continue" is possible.

Evidence-class gate rule: maximum pursuit does not mean collapsing the research control chain. Split into a new goal when crossing from source/control proof to G12 acceptance, from accepted input packet to result scoring, from result scoring to G12 post-result audit, from G12 learning to G0 synthesis, or from research artifacts to live trading behavior. These splits are a methodology feature because they prevent source clearing from silently becoming labels, denominators, validation, live-scale claims, or live logic. Inside the same evidence class, however, stopping at blocker taxonomy is a methodology failure unless the completion audit proves exact impossibility or exact external approval/access need.

Context-compaction rule: long goals must preserve their own context in committed lane artifacts, not depend on chat memory. Each long-running goal should maintain a context anchor that records controlling prompt paths, starter path, current HEAD, boundaries, inputs read, active question stack, searched roots, route decisions, blockers, missing outputs, and stop-condition status. After any resume, context compaction, interruption, or uncertainty, the session must regenerate `LIVE_STATE`, re-read the controlling prompt, the one-line starter message, `goal_session_research_discipline.md`, `research_operating_doctrine.md`, and any lane-specific doctrine from disk, re-read its context anchor/latest artifacts, and continue from the recorded state. The prompt, starter, and doctrine are enforcement sources, not background summaries; if the live conversation lost detail, disk wins. Completion audits must include instruction-coverage status so no prompt requirement is silently lost.

Small-N rule: small sample size can block validation, DSR/PBO claims, production-change readiness, or result acceptance, but it must not be used as an excuse to stop research. When `n` is too small, the session must define the exact denominator and sample floor, search approved local/committed/heavy-data roots for more eligible rows, and either build a source-hashed expansion inventory or write a precise extraction/capture manifest with source, symbols, timeframes, fields, parser, as-of rule, cache/hash path, cost/API status, forbidden fields, and owner/access requirement. "n too small" is incomplete unless paired with the exact expansion path or proof that expansion is impossible under no-leak/source-safe rules.

Negative results are first-class research evidence. A goal session must not mark a hypothesis "failed" and move on when the lane can still explain why it failed. For any negative or non-promotable result, pursue failure anatomy from the available row-level/control artifacts: what decision inputs were present, what path states followed, where the mechanism broke, whether the failure is structural, methodological, source/data-limited, underpowered, or post-hoc-contaminated, and what future preregistered hypotheses or capture fields should be created from that learning. Do this without inventing rescue thresholds or treating post-hoc explanations as validation.

## Historical Sealed Validation Doctrine

Forward shadow/live evidence is a useful realism check for current broker behavior, spreads, latency, operational drift, and capture quality. The owner has explicitly approved aggressive historical research and replay-to-deployment packaging when replay is broad, source-bound, sealed where needed, verifier-clean, stress-tested, and repaired across development/holdout partitions. Historical data can be validation-grade when it is unseen relative to the hypothesis/model-selection process and protected by a sealed partition protocol.

Future research should therefore treat historical data as multiple controlled evidence classes, not one overused bucket:

- Discovery pool: free exploration, failure forensics, mechanism search, and hypothesis generation.
- Development pool: rule shaping, source-contract construction, parser/projection design, and feature definition.
- Sealed historical validation pool: untouched rows/windows/symbols/sessions/regimes used only after a hypothesis, rule, source fields, no-leak constraints, duplicate policy, cost assumptions, and stop conditions are frozen.
- Stress/robustness pool: perturbation, cost/slippage stress, regime/session/symbol holdouts, outlier removal, and placebo/baseline checks.
- Forward shadow pool: current-market and current-system realism, capture quality, execution/cost observability, and degradation monitoring.
- Forbidden/contaminated pool: any slice whose outcomes, path labels, blocked-packet results, post-decision fields, or selection process contaminated the rule under test.

Goal sessions must not say "needs forward data" when a source-safe sealed historical validation route exists. They must first build or cite a data-partition ledger that records which historical rows have been touched by discovery/development and which remain sealed. If no sealed slice exists, they must state why and produce an expansion/search plan instead of waiting passively.

Historical validation lanes must use the strongest feasible design for the data available:

- freeze the hypothesis before opening the validation slice;
- use purged/embargoed time splits to avoid nearby-event leakage;
- run walk-forward tests when time ordering matters;
- use cross-sectional holdouts by symbol, session, side, regime, volatility state, and news/non-news state when available;
- include adversarial baselines such as random/shuffled signals, session-only, volatility-only, simple momentum/reversion, and current GTOS baseline comparators;
- run perturbation checks such as delayed entry/exit, worse spread/slippage, random missed trades, removing best trades/months, and nearby parameter variation;
- record multiple-testing debt: variants tried, parameters explored, rejected branches, abandoned ideas, and exact selection rule;
- report effective-N, duplicate concentration, regime concentration, and whether the claimed edge survives after controls.

The strongest validation sequence is now lane-dependent. For research-to-deployment packages, use:

`discovery historical -> source/control cleanup -> broad replay/development -> sealed historical or rolling holdout validation -> robustness/stress/adversarial baselines -> deployment-package dossier`.

Forward/live shadow realism is optional and additive when the open question is latency, broker behavior, spread/cost drift, capture quality, or operational drift; it is not a default gate after broad replay has already answered source-safe market/system behavior. This is not permission to promote from dirty or contaminated historical data. It is a requirement to use the available historical universe aggressively and correctly before treating future live rows as the only path to evidence. Patience belongs in owner-directed broker deployment and live capital scaling, not in local replay, repair, and deployment-package materialization.

## Required Saturation And Self-Red-Team Pass

Every substantial future research/control prompt must require a written saturation pass before completion. This is now a default hardening requirement for the assistant preparing prompts and for `/goal` sessions executing them.

The saturation pass must not be a generic checklist. It must ask what could break the lane and then pursue any same-evidence-class gap it exposes. At minimum, adapt these questions to the lane:

- What exact mistake would make one evidence class look like another, such as source-control evidence becoming an accepted result row?
- What exact mistake would let impossible, blocked, or rejected rows leak back into denominators, labels, sample size, future interpretation, or validation claims?
- Which fields look harmless but are actually post-outcome, post-cancel, broker-realized, hidden-label, path-label, or future-context fields?
- Which duplicate-key, canonical-row, projection, or denominator choice could double-count opportunity?
- Which rows are eligible under row-level counting but not under duplicate-key counting, or vice versa?
- Which label family is most likely to be over-interpreted as performance, and how does the artifact prevent that?
- Which local heavy-data roots, prior worktrees, source contracts, code paths, cached docs, or external source captures could materially change the answer, and were they searched or exactly ruled out?
- What would a skeptical G12/G0 audit reject, and how does this lane preempt that rejection?
- If the next lane finds ambiguity, should it score, exclude, split, route back to source-control, or request access? Freeze the rule.
- If a future larger cohort is added, what exact source fields, as-of rules, no-leak gates, duplicate policy, and sample-floor rules must exist before it enters the same denominator?
- What did this lane deliberately not answer, and what exact future lane owns it?

If any answer exposes an allowed same-evidence-class gap, the session must pursue it inside the current goal until it is resolved, proven impossible, or converted into an exact owner/access/source/capture requirement. "Outside scope" is acceptable only when the next step crosses into scoring, G12 acceptance, G0 synthesis, registry edit, validation, live-scale decisioning, live trading behavior, paid spend, credentials/remotes, or forbidden broker/account/order evidence.

## Hostile Edge Review Lens

The owner provided a third-party trading-system review memo on 2026-05-09. Use its useful discipline as a skeptical lens, not as an authority that overrides GTOS context or slows the aggressive research program.

Future prompts should incorporate the following filtered lessons where relevant, but lane posture matters:

- build/discovery/result-packet prompts should not lead with "fake result" framing. They should produce the strongest auditable evidence possible, build source-safe outputs when allowed, label limitations exactly, and leave independent rejection/acceptance to G12/G0.
- G12/G0 audit prompts should attack every apparent edge as possibly unsupported until source-safe evidence survives.
- ask why the edge should exist, who is structurally/behaviorally paying it, why it might persist, and what destroys it;
- separate signal edge, execution edge, risk edge, regime edge, portfolio edge, and operator/discipline edge;
- treat data quality, timestamps, sessions, spread, costs, slippage, fill realism, broker limitations, and duplicate denominators as first-class failure modes;
- distinguish discovery/control evidence from validation, production-change readiness, and live-scale decisions;
- plan later perturbation/stress tests, regime slices, execution-quality slices, and degradation monitoring once a lane reaches a legitimate result/validation stage;
- look for hidden beta, one-regime dependence, tail-risk selling, execution gaps, parameter fragility, and concentration in a few rows or duplicate groups;
- require kill/reduce/pause criteria inside any deployment-package or live-scale action plan.

Do not copy the memo's generic conservative timeline or treat it as a reason to stop source-safe research. GTOS remains in aggressive proof-or-impossibility mode. The memo's value is adversarial question quality: it should make builder sessions more curious and output-complete, and audit sessions more rigorous, not make evidence-capture sessions timid.

## Observed Process Limitations And Required Countermeasures

The science-goal program has exposed several process limitations that can waste time or weaken research if they are not explicitly handled in future prompts:

- Classification-only trap: a lane may classify blocker families and stop even though the next action is still source-safe or packet-safe. Countermeasure: same-evidence-class continuation is mandatory; classification is not completion.
- Self-audit trap: a lane can prove its own artifact but still needs independent G12/G0 acceptance before the proof becomes canonical control evidence. Countermeasure: keep evidence-class gates, but make the audit narrow and fast when the fact is obvious.
- Worktree data blindness: a worktree often lacks ignored heavy data that exists on the laptop. Countermeasure: search absolute local-heavy-data roots and prior worktrees before declaring missing data.
- Dirty-main verifier noise: live monitoring and shadow artifacts can make a verifier falsely fail if it checks the whole working tree. Countermeasure: verifiers should check the committed lane diff for forbidden live-surface changes and record unrelated workspace dirt as informational.
- Autostash/staging risk: merges on dirty main can leave unrelated files staged or conflicted. Countermeasure: after any merge/autostash, inspect `git diff --cached --name-only` before committing; never commit broad runtime dirt with a research verifier or context patch.
- Windows pycache/temp-dir friction: `py_compile` or pytest temp cleanup can fail from local filesystem permissions. Countermeasure: use controlled `--basetemp`, no-cache pytest, syntax parse fallback when bytecode writes fail, and record the distinction between environment friction and code failure.
- Public-source fragility: official webpages can be locale-specific, JavaScript-rendered, blocked, redirected, or curl-hostile. Countermeasure: save raw captures, record failed fetches separately from factual evidence, hash captures, and avoid search-result snippets.
- Proxy-source ambiguity: futures proxy evidence may not automatically prove CFD/broker behavior. Countermeasure: require explicit proxy validity language and identify whether broker-native metadata would materially change the decision.
- Prompt boxing: examples, row lists, timeframes, instruments, and artifact lists can accidentally narrow the session. Countermeasure: prompts must say examples are starting points and require anti-boxing checks.
- Context drift across long runs: chat compaction and multiple worktrees can leave sessions using stale summaries. Countermeasure: context anchors, active question stacks, current HEAD, and `LIVE_STATE` regeneration are mandatory.
- Result/control confusion: source closure, packet readiness, categorical lifecycle evidence, quarantined results, validation, and production-change readiness are different evidence classes. Countermeasure: continue aggressively inside a class, split strictly across classes.
- Production-code/deployment confusion: production-code integration, runtime config packaging, profile support, and verifier repair are not the same as broker mutation or live VPS deployment. Countermeasure: prompts must authorize code-level integration when that is the goal, then separately gate broker/account/order/deal/position actions, credentials, paid/vendor calls, remote push, and live restart/reload.
- Stale prompt pollution: old branch hashes, old process counts, old "next wave" status, old broker state, and old route blockers can steer a goal into the wrong stage. Countermeasure: prompt files may name expected anchors but must require current disk verification, route-state refresh, and replacement of stale facts before edits.
- V3-as-ledger trap: a route can leave strong Selector/Scheduler/Execution packages as inert ledgers because old prompts overemphasized research boundaries. Countermeasure: production-integration prompts must require a production-code disposition for every component: active, staged/default-off, research-only with exact missing requirement, or rejected with evidence.
- LFS pollution trap: production branches can accidentally inherit raw research ledgers. Countermeasure: production-integration prompts must require an include/exclude scope ledger, LFS review, and deployable-code branch discipline.

## What Is Still Forbidden

Maximum effort must not cross these lines unless a later owner-approved lane explicitly changes them:

- no live trading prompt, risk, execution, permission, selector, safety gate, MT5, canary, credential, remote-push, or order-behavior changes unless the active controlling prompt is explicitly a production-code integration or production-change lane and names the authorized code/config surfaces. Even then, broker/account/order/deal/position mutation, credential mutation/disclosure, paid/vendor calls, remote push, and live VPS restart/reload stay separately gated unless explicitly approved in the active turn;
- no master registry edits except proposed patch artifacts unless G0/G12/owner approval is explicit;
- no outcome scoring before an input packet is frozen and the lane explicitly authorizes a quarantined result;
- no blocked-packet outcome inspection;
- no broker actual-R inspection inside synthetic-path or lifecycle/no-fill lanes;
- no paid/API/Databento calls without a pre-call manifest, budget/free-credit proof, and explicit owner approval;
- broker-deployment or live-scale assertion requires an owner-approved or owner-requested deployment-package dossier. Broad verifier-clean replay, sealed/rolling holdout, stress, and repair evidence are valid inputs to that dossier; forward-shadow evidence is added when the remaining open field is broker behavior, latency, capture quality, or operational drift.

## Prompt Requirements

Starter prompts can be one physical line, but they should still contain:

- controlling input files;
- mandatory preflight;
- the exact lane objective;
- proof-or-impossibility wording;
- local-first search instructions;
- source/webfetch policy;
- non-outcome verification requirements;
- expected output artifact list;
- exact stop conditions;
- result-boundary fields that describe evidence class without defensive keep-closed wording;
- explicit forbidden surfaces.

## Orchestrator Artifact-Inspection Standard

The orchestrator must not treat a goal-session closeout message as evidence by itself. A closeout is a claim; the artifacts are the evidence. Before advising the owner, preparing the next prompt, or deciding whether a route is strong, the orchestrator must inspect the material files produced by the goal session.

Minimum inspection before any next-step recommendation:

- regenerate and read `.context/LIVE_STATE.md`;
- read the route completion audit;
- read the decision ledger or terminal decision artifact;
- read the verification result and output manifest;
- read the next prompt file or prompt pack;
- read blocker, fail-closed, repair, prospective-capture, source-inventory, route-ranking, synthesis, and saturation/self-red-team ledgers whenever those artifacts exist or affect the next step;
- inspect large JSONL/large matrix files with targeted commands for schema, counts, representative rows, status distributions, and suspicious edge cases rather than relying on their filenames or summaries;
- compare artifact facts against the pasted closeout message and state any material mismatch;
- harden the next prompt only after understanding the actual artifact facts.

If the orchestrator has not inspected a material artifact, it must say so explicitly and avoid high-confidence strategic conclusions. For high-value gates, inspecting only the closeout message or only the next prompt is inadequate orchestration.

## One-Line Starter Message Standard

When preparing a `/goal` run from a controlling prompt file, the starter message must be treated as an execution contract, not a casual short description. The controlling prompt file carries the full detailed objective; the starter message tells the goals runtime how to execute it.

Default rule: use one physical line with no blank-line formatting, reference the controlling prompt path, and include the strongest behavioral constraints in compressed form. Do not rely on chat memory to supply any of these constraints.

The starter should explicitly contain, in this order:

1. `/goal Follow the full controlling prompt in <PROMPT_PATH> as the complete objective`.
2. Mandatory preflight and context refresh before work.
3. No reliance on chat memory or compaction memory, plus explicit reread of the controlling prompt, starter, doctrine, and latest route artifacts after context compaction/resume/interruption/uncertainty.
4. Exact evidence class and exact forbidden surfaces.
5. Proof-or-impossibility to the full end inside the evidence class.
6. The lane-specific terminal closure requirement, such as `55/55 fields closed`, exact packet count, exact source closure, exact blocker list, or exact result/audit ledger.
7. Mandatory builder/verifier/focused tests or the lane's strongest equivalent.
8. No unresolved placeholders, vague blockers, or lazy "future work" where same-evidence-class pursuit is still available.
9. Required result-boundary fields: evidence class, forbidden surfaces, runtime-effect boundary, and source-use state when applicable.
10. Blocker rule: pursue until cleared, proven impossible from approved routes, or reduced to an exact owner/access/source/capture approval requirement.
11. Completion rule: mark complete only when the controlling prompt's completion standard is fully satisfied with scoped commits and closeout verification.
12. For production-code integration lanes: explicit authority for code/config/profile/verifier/launcher changes, explicit separation from broker/deployment mutation, V3/component runtime disposition, LFS production-branch scope, and current-disk verification of branch hashes instead of stale chat facts.

Canonical one-line template:

```text
/goal Follow the full controlling prompt in <PROMPT_PATH> as the complete objective; do mandatory preflight and context refresh first; read this starter, the controlling prompt, goal_session_research_discipline.md, research_operating_doctrine.md, lane-specific doctrine, and latest route artifacts from disk after any context compaction/resume/interruption/uncertainty; do not rely on chat memory; stay <EVIDENCE_CLASS_ONLY> with no <FORBIDDEN_SURFACES>; pursue proof-or-impossibility to the full end inside this evidence class; complete only with <LANE_SPECIFIC_TERMINAL_CLOSURE>, mandatory builder/verifier/focused tests, zero unresolved vague placeholders, exact future source/schema/redaction/fail-closed/test/rollback/G12-or-G0 criteria where applicable, scoped commits, closeout verification, result-boundary fields, source-use state, and runtime-effect boundary; if any blocker appears, pursue until cleared, proven impossible from approved routes, or reduced to an exact owner/access/source/capture approval requirement, and mark complete only when the prompt file's completion standard is fully satisfied.
```

For `/goal` objective length limits, keep the starter under the CLI limit by moving detailed instructions into the controlling prompt file and using the one-line starter only to bind the runtime to that file and the hardening standard. If the starter still becomes too long, preserve the order above and compress wording, but do not remove preflight, evidence-class boundary, proof-or-impossibility, terminal closure, result-boundary fields, blocker rule, or completion rule.

## Stop Condition

A goal session is not complete merely because it read the obvious files. It completes only when it has either:

- built the requested proof/control/input artifacts with machine-checkable ledgers, or
- proven the requested artifact cannot be built from current approved inputs and recorded saturation evidence plus the exact next unblocker.

Every blocker must be actionable. "Needs more data" is insufficient unless it names the exact data, source, field, schema, logger, parser, legal/access proof, or owner approval.

When the artifact is a negative result audit, completion also requires a failure-forensics answer: what failed, how it failed, which available evidence supports that diagnosis, which questions remain genuinely unanswerable from approved inputs, and what exact next capture/test would close them.
