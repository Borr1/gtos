## Absolute Vision

The end state is not a better single strategy. It is a trading operating system with:

- a living market model;
- broker-real execution body;
- portfolio risk brain;
- market-aware selector;
- tick-realistic execution-policy engine;
- replay/digital-twin engine;
- ML learning system;
- autonomous repair companion;
- command center;
- continuous research-to-production conversion loop.

The system should understand the market as a structured flow field, not as isolated buy/sell signals. It should know the condition of every market it trades, the condition of its own data, the condition of the account, the quality of each candidate, the true broker constraints, and the correct response when market behavior changes.

Operational consciousness means the system maintains explicit awareness of:

- market state;
- candidate state;
- portfolio exposure state;
- broker truth state;
- data freshness state;
- source completeness state;
- execution lifecycle state;
- model confidence and uncertainty state;
- stale-system leakage state;
- research/validation status;
- production-change status.

The ultimate system does not need perfect prediction. It needs correct adaptation. It should know when to enter, wait, reduce, skip, reverse its assumption, let a trade breathe, cut exposure, or treat the data itself as untrustworthy.

## Absolute Capability Map

### Market Perception Layer

The system should maintain a live market whiteboard over all traded instruments:

- ticks;
- M1/M5/M15/H1/H4/D1 bars;
- spread and spread-to-risk;
- liquidity sweeps;
- displacement;
- failed displacement;
- absorption;
- volatility expansion and contraction;
- trend/range/regime;
- session timing;
- kill-zone timing;
- news/calendar context;
- cross-market and cross-symbol correlation;
- risk-on/risk-off flow;
- metals/index/FX/oil/crypto context;
- broker market-hours state;
- broker stop/freeze levels;
- symbol-specific execution friction.

The live decision should not read as "XAUUSD long signal." It should read as a full state:

- what the candidate is;
- why it exists;
- which selected cell or bridge proves it;
- whether the source is complete;
- whether the spread/cost is acceptable;
- which execution policy is appropriate;
- whether portfolio risk can absorb it;
- what the broker can actually execute;
- what would invalidate the trade;
- what lifecycle manager owns it after entry.

The meta-selector should not hardcode one Friday rule. It should learn which mechanisms survive across broad selected denominators, sealed partitions, symbol/session holds, stress conditions, and broker-real cost assumptions.

### Portfolio Scheduler

The scheduler should govern admission by actual account exposure, not stale count caps.

It should compute:

- current balance and equity;
- day-start baseline;
- realized broker PnL;
- open worst-case SL risk;
- pending worst-case SL risk;
- new candidate worst-case risk;
- partial risk release;
- BE risk release;
- spread/slippage/commission buffer;
- same-symbol exposure;
- correlated cluster exposure;
- daily internal overlay;
- external prop daily and total limits;
- realized cushion expansion;
- drawdown compression;
- portfolio priority if multiple candidates compete.

The scheduler should allow many small strong trades when total exposure is inside limits and block one bad trade when it consumes too much risk. It should never use a stale "max two trades" style cap as the true authority for vNext when money-risk proof is available.

### Execution Policy Engine

The execution layer should choose and manage exits based on evidence, not fixed habit.

It must evaluate and implement, when proven:

- partial-BE runner;
- momentum exhaustion;
- trailing runner;
- time-stop;
- fixed comparator;
- BE-after-trigger comparator;
- no-trade;
- symbol/session/origin-specific execution policies;
- policy exceptions where another exit dominates.

Every policy must be tick-realistic and broker-feasible:

- exact tick ordering;
- bid/ask side;
- spread at trigger;
- same-bar ordering;
- stop/freeze levels;
- modify retcodes;
- latency assumptions;
- partial-close ticket identity;
- residual ticket management;
- commission/swap/slippage;
- broker minimum stop distance;
- failure handling.

Proxy MFE is not enough. Every promising proxy must be converted into executable tick/broker proof before production use.

## Current Limitations Driving The Full Moonshot Repair Loop

The limitations below are not a ranked top list. They are the current known and inferred gap map from the absolute vision.

### Integration Limitations

- The accepted V4/KIAP stack is integrated enough to run production-called replay through `V4DecisionCycleCore`, Scheduler V4, Selector V4, Execution Manager V4, SimulatedBroker, and tick-first selected path truth.
- The current limitation is no longer lane packaging. It is behavior quality under replay: scheduler regret, weak accepted trades, risk-headroom lockout, stale partial-BE residue, cost flips, and holdout degradation.
- Shared-code repair still needs one owner route at a time for overlapping scheduler/selector/risk/execution files.
- Route artifacts and code changes become current build truth only when merged, committed, verified, and reflected in current context.

### Selector And Edge Limitations

- The final meta-selector does not exist yet.
- Current selected subsets are promising but not enough for final moonshot selection.
- Friday evidence alone cannot be allowed to become the system boundary.
- Broad selected denominator stress over the full selected surface is still pending.
- Selected-cell risk proof remains a critical live-decision field.
- Some Friday replay rows used effective risk projection because selected-cell risk was missing/zero.
- Generic selected-cell/risk bridge labels must be eliminated wherever current source proof can resolve them.
- There is no final source-bound rule set that ranks all symbols/sessions/origin families/regimes under costs and stress.
- Avoid/inverse intelligence is not fully converted into live filters or meta-selector features.
- Positive and negative failure anatomy is not yet mined across all historical days with Friday-level depth.

### Portfolio Scheduler Limitations

- The ideal real-money exposure scheduler is not fully live-authoritative yet.
- Open + pending + new risk in dollars is not yet proven as the sole vNext admission authority everywhere.
- Stale count/session/KZ caps may still exist outside the repaired vNext path.
- Same-symbol multi-ticket lifecycle is still not a mature supported behavior.
- Correlation cluster exposure is not yet a full scheduler authority.
- Portfolio priority between simultaneous candidates is not final.
- Daily cushion expansion after realized gains needs full runtime proof.
- Drawdown compression and recovery behavior need broader replay stress.
- Pending order risk and partial risk release need consistent broker-real truth across all paths.

### Execution Limitations

- Current execution policy optimality is not proven across KIAP development/repair/holdout.
- `partial_be_runner` is not a default-v4 virtue after KIAP; it is a measured damaged family unless a later evidence-routed exception proves otherwise.
- Trailing policy remains unproven until tick-realistic broker-feasible simulation exists.
- Time-stop and hybrid exits need strict stress on selected/broker-ready denominators.
- Execution policies are not yet selected by a final evidence-backed policy router.
- Same-bar ordering, trigger ordering, and bid/ask side need strict handling in all replay.
- Broker stop/freeze modify feasibility is not fully integrated into every policy simulation.
- Latency and retcode behavior are not fully modeled.
- Partial close and residual management are improved, but multi-ticket proof remains incomplete.
- BE/TP modify failure diagnostics need final integrated runtime verification.
- False close handling is repaired in Lane06, but final merged runtime must enforce it everywhere.

### Broker Truth And Cost Limitations

- Two Friday residual positions had final net-R pending broker close in Lane06 evidence.
- Broker net-R is not yet the universal outcome authority across every artifact and runtime packet.
- Local projected PnL can still appear in older artifacts and must not dominate broker truth.
- Commission, swap, spread, slippage, and retcodes are not yet fully used in selector/scheduler decisions.
- Cost calibration by symbol/session/regime is not mature.
- Broker history joins must become robust for every order, deal, partial, residual, modify, and close.
- Telegram parity is improved but must be broker-truth-driven.
- Manual/client intervention classification must remain explicit.

### Market Awareness Limitations

- The main decision loop is still fundamentally M15-cadence, with M1/tick capture around it.
- There is no full all-symbol event-driven tick/M1 decision loop.
- M1/tick capture exists, but not every layer reasons from lower-timeframe state.
- HTF/M15/M1/tick fusion is not a mature unified market-state model.
- Cross-market/correlation awareness is still limited.
- Macro/calendar context is not a deep predictive regime layer.
- News impact is not yet modeled as a first-class adaptive state.
- Spread and liquidity regime awareness are still basic.
- Session context exists, but not full market-session intelligence.

### Data And Source Limitations

- Historical source completeness varies by field, symbol, timeframe, and artifact.
- Tick/M1 availability differs across periods and symbols.
- Some historical system-state truth cannot be reconstructed if it was never logged.
- Broker intent/order/lifecycle truth cannot be invented from price movement.
- Data quality, timezone, session boundary, and duplicate-key issues remain first-class risks.
- Source contracts and no-leak rules must be explicit for every future ML/replay label.
- Older artifacts still contain stale labels, old production framing, and comparator language.
- Current worktree still has runtime/shadow/program-control dirt that must not become context pollution.

### Replay And Validation Limitations

- The full "current runtime as-of" digital twin is not complete yet.
- Friday microscope is not enough to validate production behavior.
- One-day lift can expose a mechanism but cannot prove stable expectancy alone.
- Broad selected replay must include costs, stress, concentration, splits, exposure, and source completeness.
- Sealed historical validation partitions are not yet complete for the next v2 package.
- Forward shadow validation infrastructure exists in pieces but is not the final rolling evaluation engine.
- Every replay must distinguish raw candidates, selected candidates, broker-ready candidates, accepted trades, and actual broker outcomes.
- Raw candidate tournaments can mislead if treated as whole-system performance.

### ML Limitations

- No final vNext ML feature store exists.
- No final vNext label store exists.
- No years-scale microscopic candidate/path dataset exists yet.
- No trained model is production-ready.
- No model family has been selected by sealed evaluation.
- No ML model currently owns live decision authority.
- No ML uncertainty/OOD/drift layer is production integrated.
- No ML feature attribution layer is available for candidate autopsy.
- No ML policy-selector is broker-cost-aware yet.
- No ML system has been trained on the Friday-style microscopic anatomy across many historical days.
- Existing ML/shadow files are not enough; they are inputs and prior intelligence, not the final moonshot ML system.

### Orderflow And Depth Limitations

- Orderflow/depth is not core to current vNext selection.
- Sierra/Databento/depth data is not integrated as a validated live feature set.
- Futures-to-CFD proxy mapping needs symbol-specific proof.
- Trades-only orderflow and depth/MBO/heatmap intelligence must be separated.
- Depth pulls should be event-based and cost-controlled.
- Orderflow should become selected-window intelligence, not a magic universal filter.

### AI Companion Limitations

- AI is not yet a permanently running verified repair companion.
- AI API reliability, schema stability, and input validation are not production-proven.
- Paid AI calls are not yet governed by a final economic testing harness.
- AI prompt inputs need pre-send null/staleness/schema validation.
- AI outputs need deterministic fallback and auditability.
- AI is currently better suited for supervision, analysis, and repair than core edge.

### Operations And Command Center Limitations

- There is no final unified command center.
- Current context is improved, but active lane/runtime dirt remains.
- Current state is distributed across route artifacts, logs, and context docs.
- Agents still need explicit reading paths to avoid stale material.
- Production-change packages are not yet one-click or fully standardized.
- Live activation, canary, rollback, and post-merge verification are not final for v2.

### Research Process Limitations

- Goal sessions can still drift into ledger-only completion if prompts are weak.
- Parallel lanes can create shared-code conflict if commit ownership is not enforced.
- Completion messages are claims; artifacts must be inspected from disk.
- Context compaction can cause stale re-anchors unless route anchors are written and reread.
- Top-N summaries can hide important rare details unless full ledgers are preserved.
- The research map still needs stronger primitive coverage tracking.
- The future ML/moonshot route must avoid passive "study forever" loops by forcing every study into code, data products, model training, filters, scheduler logic, or explicit rejection.
