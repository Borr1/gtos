## 4. The finding that changes D-1: the payload is regenerable

Either version reconstructs the other **byte-exactly**, bidirectionally, and the transform is
idempotent when the stamp already matches:

```
a5bcc0f8 --retime('2026-07-16T11:09:40Z')--> 19365f60   exact: True
19365f60 --retime('2026-07-13T01:27:31Z')--> a5bcc0f8   exact: True
```

Method (`jsonl_retime_and_rehash`, recorded formally in the JSON): per line, `json.loads` (key order
preserved), set `generated_utc`, recompute `row_hash_sha256` by the derivation above, re-serialise
with `json.dumps(row, separators=(', ', ': ')) + '\n'`, concatenate.

**This is the strongest part of the record.** It means custody of *one* version is custody of *both* —
the contract-bound bytes are recoverable from HEAD alone even if every copy of them were destroyed
tonight. `tests/test_d1_sleeve_registry_custody.py::test_regeneration_recipe_is_byte_exact_and_bidirectional`
re-proves it on every run, so it cannot rot into a claim.

It also *narrows* D-1 to its true residue: the danger was never really "the bytes are unrecoverable",
it was "nothing checked, and nobody could tell". Both halves are now fixed.

## 5. Commit the bytes, or keep a custody record? — recommendation

**Recommendation: do both, in this order — the custody record now (done, this artifact), and commit
the `19365f60` bytes as a small follow-up. The follow-up is worth doing and cannot be done by this
session.**

### For committing the bytes

1. **It is the only option that puts the payload under git custody.** The record + regeneration proof
   make the *content* recoverable, but the `19365f60` **object** stays unreferenced and stays deletable
   by `git lfs prune`. Only a pointer naming it fixes that.
2. **It makes the sealed campaign reproducible from git.** Today it is not
   (`IMPLEMENTATION_STATE.md:87-95`): the bound version exists only in `/repo`'s *working tree*, one
   `git checkout` away from gone. A fresh clone on a new machine currently cannot satisfy R1/R2 at all.
3. **It turns a tolerated yellow into a real green.** `drifted=1` would become `drifted=0`. A tripwire
   whose documented baseline is 1 trains every reader to look past it — the exact false-green pattern
   this session exists to remove. At 0, *any* drift is signal.
4. **Nothing expects `a5bcc0f8`.** Four sealed artifacts expect `19365f60`. No test asserts either hash
   or `generated_utc` (checked across `tests/`). The 53 decision-bearing fields are identical, so no
   behaviour moves.
5. **Cost is ~nil.** 205,754 B, already LFS-tracked and **already in the local object store**. The
   commit adds a 131-byte pointer blob; the 205 KB object is not newly created. Against a 2.5 GB tracked
   tree this is 0.008 %.
6. **It does not trip H1.** H1 fires when you *edit* a bound file so it stops matching. This makes the
   bound file start matching in every checkout — it removes a fail-closed condition rather than creating
   one, and it cannot produce a *second* drifted path.

### Against

1. **It invalidates two documents this session may not edit.** `WAVE_3_WORKING_AGREEMENT.md:163-165`
   and `WAVE_3_README.md:78-80` both state `drifted=1` is a known false alarm. Commit the bytes without
   amending them and you have manufactured a fresh false-green — a document asserting a property the
   system no longer has, which is precisely the defect class being swept.
2. **`a5bcc0f8` becomes the newly-orphaned version.** Mitigated on three independent legs: it stays
   referenced by two historical commits (`95105914`, `a6304e20`), it is on the `origin` remote, and it
   is regenerable from `19365f60` by the same proven transform. The custody record covers both versions
   symmetrically, so this is a rename of the risk, not a transfer of it.
3. **It writes to a contract-bound path in a branch four other sessions are working in.** A
   coordination cost, not a technical one.

### Net

The arguments against are all *sequencing*, not substance. The arguments for include the only
remaining unmitigated exposure. **Commit the bytes** — but in a single commit that also amends
`WAVE_3_WORKING_AGREEMENT.md:163-165` and `WAVE_3_README.md:78-80` from "`drifted=1` is a known false
alarm" to "`drifted=0`; **any** drifted path is signal", and flips the two `in_git_history` flags in
`D1_SLEEVE_REGISTRY_CUSTODY.json`. `test_git_history_flags_are_still_true` fails until that flip is
made, by design — the record is not allowed to keep calling a version orphaned after it stops being one.

knowing the audit tree.

Location does not affect enforceability: the test resolves both by repo-relative path.

## 8. Custody test

`tests/test_d1_sleeve_registry_custody.py` — 9 tests. It reads the JSON record and checks that custody
is real: the in-tree payload resolves to a recorded version (hydrated, or a pointer whose object is
local); every recorded version has a surviving copy **or** a working regeneration path; the regeneration
recipe actually reproduces both versions byte-for-byte; the three sealed contracts still bind the hash
the record claims; and no probed path is ever under iCloud.

Machine-local holds **skip with a reason** when absent. A missing or wrong **in-tree** copy is a hard
failure — it never skips.

Verified by mutation (each simulated in a sandbox outside the repo; see §9 of the task report):
deleting the payload, corrupting one byte, an un-hydrated pointer with no local object, every recorded
copy vanishing with a broken regeneration, a hold copy whose bytes changed, and a contract silently
re-sealed to a different hash — **all fail loudly**. Every copy vanishing while regeneration still works
**passes**, correctly. Only-machine-local-and-absent **skips with the reason naming the copies**.
