## 5. The live-bounded carrier

`src/components/ultimate_book/lane_weights.py` implements one signed, all-or-neutral
`gtos.lane_weights.v1` envelope:

- HMAC-SHA256 binds namespace, exact sleeve scope, the complete vector, declared **[0.50, 1.15]**
  band, evidence digest, issue time, effective day and expiry. The external key must be at least 32
  bytes; POSIX group/other permissions and symlinks are refused.
- Missing, unreadable, malformed, stale, future, wrongly scoped, out-of-band or badly signed input
  yields **1.00 for every scoped sleeve** and an ERROR. No partially valid member can leak through.
- A previously unseen non-neutral vector is admitted only in the first five minutes of its UTC
  effective decision day, then atomically persisted at
  `pipeline_state/ultimate_book/<namespace>/lane_weights_latch.json`. Every same-day restart
  re-verifies and reuses those signed bytes. A corrupt latch or persistence failure is neutral.
- `run_book.py` requires the weights path, key path and explicit `--tags` scope as one launch
  contract, and validates/latches before the first MT5 connection. With no lane arguments, the
  feature is disabled and existing behavior is unchanged.
- `book_engine.py` injects only an in-memory copy into the existing
  `ultimate_book_learning_rerate` seam. Config/profile bytes do not move. The running-conviction
  pre-count receives the same rerate so a braked sleeve cannot survive in the Kelly count.
- Every cycle and management packet exposes `lane_weight`, `lane_weights_by_sleeve`, signature
  status, controller day, band, source/evidence digests, effective day, expiry and issue time.
- The existing sizer applies the multiplier before the gross-risk governor; soft/hard stops and
  breach flatten remain downstream and senior.

`scripts/gtos_lane_weights.py` is the broker-free key/sign/verify/telemetry tool. The current signed
declarations are effective 2026-08-02 through 2026-08-08 UTC inclusive and bind the byte digest of
`CO_CURRENT_VECTOR_V1.json`. The private 32-byte handoff key remains outside git at

   membership on entry day rather than decision day; both ran before the sparse spread-model
   dependency had been materialized. I did not rewrite the ledger. The 18 failed cells remain as
   unbilled, superseded rows and the 11 corrected logical cells are idempotent.
2. An early metadata grep touched aggregate fields associated with the protected blackout. I
   stopped and excluded those values from every calculation and report. The final AA reader parses
   membership only and explicitly rejects `daily_net_r`, `daily_cost_components` and blackout
   aggregate keys; the estate/BTC readers enforce the label boundary before outcome decode. No
   protected row outcome entered the work.
3. The signer initially worked as a module but failed when invoked directly from the repo because
   `scripts/` displaced the repository root on `sys.path`. I added a repo-root bootstrap, reran the
   direct sign/verify path and rebuilt the carry payload.
4. I first asked the carry verifier for the American-spelled `behavior` mode. Its declared CLI is
   `behaviour`; the valid mode then required the external key as intended and passed. No receipt or
   behavior changed.
5. I could not verify a full hash for the host's current supervisor from local evidence—only its
   receipt prefix and semantic contracts exist here. Overwriting it from mainline would discard
   host-only ceremony history, so the package carries an anchored semantic diff and makes exact
   host preflight a hard stop rather than guessing.
