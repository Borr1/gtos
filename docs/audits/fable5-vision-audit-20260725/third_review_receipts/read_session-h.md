Context: the live book computes **nine** independent day notions (note §1, table with file:line for each), of which #1 (UTC date of the last closed bar's open, `bar_provider.py:86-88`) keys the correlated-unit bucket, the Kelly count, the running store, and both placement caps; the 14 `mx_*` sleeves already overwrite it with the runtime date (`market_expansion_d1.py:147-160,217-221` [VERIFIED]). The collision (D2) is 4 consequential cycles, worst 1.66× same-bar spread. §4 tabulates four candidates, each **measured** against the 4 consequential cycles rather than argued (the task said three; the note's table has four rows — B94 calls it three because the server-midnight row is a measured anti-option):

1. **Re-stamp `vol_compression` like the `mx_*` sleeves** — unifies **1 of 4**. Trivial one-line change, negligible envelope effect (merges one sleeve's D1 intents into the runtime bucket). Does not touch the same-sleeve `idxrev` case, i.e., repairs the symptom least representative of the mechanism.
2. **Key the day off the bar close instead of its open** — unifies **2 of 4**. Fails on the note's own headline cycle (a bar 2 days stale) and on the same-sleeve case. Worse than it looks: it changes `decision_day` for **every** sleeve and bar crossing midnight, so every correlated-unit bucket and both placement caps shift broadly for a 2-of-4 repair — the widest blast radius per unit of fix.
3. **Move #1 from UTC to server midnight** — unifies **0 of 4**. Server midnight is 21:00/22:00 UTC, exactly where D1 bars close, so it puts the boundary *through* the collision. Measured strictly worse; reject.
4. **Key the day off the cycle runtime** (the existing `mx_*` convention) — unifies **4 of 4**, the only bar-independent option and therefore the only one that can unify the `idxrev`-vs-`idxrev` case; also the only one that reduces the book from two day-key conventions to one instead of shuffling them.

**Risk-envelope consequences of the runtime key** (note §4, quantified as far as the evidence allows): it merges intents currently split across two `(decision_day, cluster)` buckets — fewer independent correlated units on affected cycles, **tightening** the envelope (safe direction) — while simultaneously raising the Kelly count for the previously-under-binned unit, raising that unit's size by up to 1.66× (unsafe component). Net effect not one-signed; the note says an MC pass on the real book is required, and correctly did not apply the change (funded-account sizing, B54 Part 2 owner territory).

**My recommendation to the owner: adopt the runtime day key (option 4), conditional on an MC pass, and take none of the partial fixes.** Reasons: (a) it is the only fix that measured 4/4 — the other bar-derived keys are provably incapable of the same-sleeve case; (b) it is not a new convention — 14 of 29 live sleeves already use it, so the change is a unification, not an innovation; (c) its unsafe component is bounded and measurable: SleeveBookPolicy can re-run the 617 unit-bearing cycles plus synthetic midnight-boundary stress under the runtime key in seconds, producing the exact envelope delta the decision needs (~0.5–1 session, see §4); (d) sequencing risk is currently minimal — the book is placement-deactivated under OD-1, so the change re-certifies a challenger, not a live book; deciding now is cheap, and the certified-envelope objection carries less weight for a book whose certification already describes a deactivated configuration; (e) side benefit for measurement: it eliminates the 25 two-date EVIDENCE_GAP cycles and would have made the 2 unexplained §6b placements comparable — the fix pays for itself in future validation coverage. Present to Borhen as: one-line decision, MC evidence attached, implemented first as a flagged variant in SleeveBookPolicy, ported to the live book only at the next controlled deploy. Explicitly recommend against option 1 as a standalone (it would look like a fix while repairing 1 of 4) and against option 2 (widest blast radius, fails its own headline case).
